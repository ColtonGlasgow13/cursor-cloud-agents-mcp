# cursor-cloud-agents-mcp

An MCP (Model Context Protocol) server that puts [Cursor Cloud Agents](https://cursor.com/docs/cloud-agent/api/overview)
inside whatever agent you already use — Claude Code, Cursor, Codex CLI, Windsurf, VS Code. It wraps the
`https://api.cursor.com` v1 REST API in 18 typed tools, so a model can launch a cloud agent on a GitHub repo,
watch it work, and collect the resulting branch or pull request without you writing any glue.

The interesting part is the monitoring. Cursor streams run progress over Server-Sent Events, but MCP tool calls
are request/response — a tool cannot hold a stream open for ten minutes. This server bridges the two: it opens
the stream, drains it for a few seconds, returns the events it collected plus a resume cursor, and tells the
model exactly what to do next. Auth, the ~20 requests/minute budget, GET-only retries, SSE resume via
`Last-Event-ID`, and the API's error codes all live in one place instead of being reinvented per prompt.

> **Status:** wraps a **public beta** API. Cursor says v1 "may change before general availability", and its
> OpenAPI spec already disagrees with its own prose in places. Response parsing here is deliberately loose:
> unknown fields pass through and unknown enum values are surfaced as strings with a warning rather than
> throwing. Expect occasional drift.

## Install

All harnesses run the same thing: `npx -y github:ColtonGlasgow13/cursor-cloud-agents-mcp`. There is no npm
publish — npm installs the package straight from GitHub and its `prepare` script compiles TypeScript at install
time (which is why no `dist/` is committed). **The first launch takes roughly 20–40 seconds** while npm installs
dev dependencies and runs `tsc`; later launches are fast.

Because the repo is private, the machine needs GitHub access (an SSH key on `github.com`, or a token in the git
credential helper). The `github:` shorthand uses whatever git credentials are already configured and is verified
to work against this private repo. If it fails to resolve on your machine, use the explicit SSH form instead —
swap it into any snippet below:

```
git+ssh://git@github.com/ColtonGlasgow13/cursor-cloud-agents-mcp.git
```

Pin a ref for reproducibility: append `#v0.1.0` or `#<commit>` to either spec.

Every snippet below is also generated by the CLI itself:

```bash
npx -y github:ColtonGlasgow13/cursor-cloud-agents-mcp print-config claude-code
# harnesses: claude-code | cursor | codex | windsurf | vscode | json
# flags: --name <serverName> --source <npx-spec> --key <apiKey>
```


## Getting an API key

| Key type | Where | Notes |
| --- | --- | --- |
| **User key** | Cursor Dashboard → API Keys (`cursor.com/dashboard/api`) | Acts as you. `whoami` returns your user id and email. |
| **Team service-account key** | Team settings → API Keys | Acts as the organization; `whoami` returns only the key name and creation date. Required for some team-scoped operations. |

Keys look like `crsr_…`. They are never logged or echoed by this server. Check one without touching any agents:

```bash
CURSOR_API_KEY=crsr_... npx -y github:ColtonGlasgow13/cursor-cloud-agents-mcp doctor
```

## Tools

| Tool | What it does | Key inputs |
| --- | --- | --- |
| `launch_agent` | Creates an agent and starts its first run. Can return `pending: true` — see below | `prompt`, `repos?`, `model?`, `mode?`, `autoCreatePR?`, `agentId?`, `launchTimeoutMs?` |
| `send_followup` | New run on an existing agent, same workspace and history | `agentId`, `prompt`, `mode?` |
| `cancel_run` | Terminally cancels the active run | `agentId`, `runId` |
| `archive_agent` / `unarchive_agent` | Reversible cleanup / restore | `agentId` |
| `delete_agent` | Permanent deletion | `agentId`, `confirm: true` |
| `get_agent` | Full agent record incl. `latestRunId` | `agentId` |
| `get_run` | Run snapshot + `isTerminal`, `prUrls`, `suggestedPollDelayMs` | `agentId`, `runId` |
| `get_run_events` | SSE→poll bridge: events + `nextEventId` cursor | `agentId`, `runId`, `afterEventId?`, `maxWaitMs?`, `eventTypes?` |
| `wait_for_run` | Blocks until terminal or the deadline | `agentId`, `runId`, `maxWaitMs?` |
| `list_agents` | Paged agent list (`items` + `nextCursor`) | `limit?`, `cursor?`, `prUrl?`, `includeArchived?` |
| `list_runs` | Paged run list for one agent | `agentId`, `limit?`, `cursor?` |
| `whoami` | Identity behind the API key | — |
| `list_models` | Model ids for `launch_agent` (cached 10 min) | `refresh?` |
| `list_repositories` | Connected GitHub repo URLs (cached 10 min, **1 req/min**) | `refresh?` |
| `get_usage` | Token usage per agent/run (early access) | `agentId`, `runId?` |
| `list_artifacts` | Files under the workspace `artifacts/` dir | `agentId` |
| `download_artifact` | Presigned URL (~15 min) for one artifact | `agentId`, `path` |

## How to monitor a run

The whole point of the server is that this loop is spelled out for the model in every tool response.

**Streaming (you want to see progress):**

1. `launch_agent` → `{ agentId, runId }` (or `{ pending: true, agentId }` — see below).
2. `get_run_events` with those ids and no `afterEventId`.
3. If `isTerminal` is false: sleep `suggestedPollDelayMs` (≈5s), then call `get_run_events` again with
   `afterEventId = nextEventId`. Repeat.
4. When `isTerminal` is true: `get_run` for `run.result` and `prUrls`. A terminal run does **not** always have
   `result` — cancelled, errored and expired runs usually have none, and the hint says so instead of promising it.

**Blocking (you only want the answer):**

1. `launch_agent` → `{ agentId, runId }`.
2. `wait_for_run` (default 55s). If it returns `isTerminal: false` that is **not an error** — call it again with
   `afterEventId = lastEventId`. Cloud runs commonly take several minutes.

**If `launch_agent` returned `pending: true`:** the run id does not exist yet. Poll `get_agent` with the
`agentId` from that result about every 10s (it 404s until the agent appears), then `list_runs` for the first
`runId`, then rejoin either loop above at step 2.

Three things a live run proved you cannot assume:

- **Do not depend on a `done`/`result` event** — some runs finish without one (a 3-minute plan-mode run emitted
  neither, nor an `error`; only the sticky `status` framing event and the run record showed it had finished).
  `isTerminal` is derived from the run status, so trust that.
- **`git.branches` is not proof of a push.** Cursor reserves a branch name when the run starts: a live run
  reported `cursor/mcp-live-…` for a ref that never existed on GitHub. `branches` lists reserved/target branch
  names; a `prUrl` is the only reliable signal that work was published.
- **Plan-mode runs keep the plan in an artifact**, not in `result` (`result` was just the closing line "…Let me
  write the plan."). Call `list_artifacts`, then `download_artifact` on `artifacts/plans/<name>.plan.md` —
  minting that presigned URL takes 30–40s.

**Rate-limit budget.** Cursor's documented default is ~20 requests/minute per user, and this server enforces the
same budget locally so you fail fast instead of collecting 429s. Every stream open and every snapshot is one
request. Polling `get_run_events` every 5s costs 12 requests/minute — most of your budget for one run. Prefer
`wait_for_run` (one stream open per 20s window plus one final `get_run`) when you do not need intermediate
output, and never poll two runs at 5s intervals at once. `list_repositories` is far stricter (1/minute, 30/hour) and is cached for 10 minutes; this
server refuses extra calls locally rather than burning the server-side allowance.

If the local budget is exhausted, tools return `LocalRateLimitError` with a "try again in Ns" message and **no
request is sent**.

### Why `launch_agent` may return pending

`POST /v1/agents` is **not** fire-and-forget: it blocks until Cursor has provisioned the first run. A trivial
no-repo agent was measured at **61.9 seconds**, which is past the MCP SDK's 60s default tool timeout — so a
default-configured client would abort the call *after* the agent had been created and billed, leaving the caller
with no `agentId` and an orphan agent.

So `launch_agent` races the create against `launchTimeoutMs` (default **45000**, min 5000, max 120000, kept under
that 60s default). If the timer wins, the tool returns a normal **success** result with `pending: true`, the
`agentId` it pre-assigned, `runId: null`, and a hint spelling out the recovery loop; the create keeps running in
this server's background and its outcome is logged to stderr. Nothing is lost and nothing is retried.

To make that recoverable, every launch that can carry a client-supplied id gets one: this server generates
`bc-<uuid>` itself when you do not pass `agentId`, and reports `agentIdSource: "caller" | "client" | "server"`.
Re-sending that id is safe — the API answers `409 agent_id_conflict` and the tool returns the existing agent with
`alreadyExisted: true` rather than launching a second one. The exception is `envVars`, which forces a
server-minted id: those launches get a generated `name` (`mcp-launch-<8 hex>`) instead, and a pending result tells
you to find the agent with `list_agents`. Lower `launchTimeoutMs` if your client's tool timeout is under 45s.

## Error semantics

| HTTP / condition | Error class | What it means and what to do |
| --- | --- | --- |
| 401, 403 `unauthorized`/`api_key_not_found` | `AuthError` | Bad or missing key. Fix `CURSOR_API_KEY`; run `doctor`. The key is never echoed. |
| 403 `feature_unavailable` | `FeatureUnavailableError` | Early-access feature (usually `get_usage`) is off for the account. Do not retry. |
| 403 other | `ForbiddenError` | Plan or role restriction. Retrying will not help. |
| 404 | `NotFoundError` | Wrong or deleted id. Message names what was looked up. |
| 409 `agent_busy` | `AgentBusyError` | A run is already active. `wait_for_run` or `cancel_run`, then retry. |
| 409 `agent_archived` | `AgentArchivedError` | Call `unarchive_agent` first. |
| 409 `agent_id_conflict` | `AgentIdConflictError` | That `agentId` exists. `launch_agent` handles this itself and returns the existing agent with `alreadyExisted: true`. |
| 409 `run_not_cancellable` | `RunNotCancellableError` | Run already terminal. Read it with `get_run`. |
| 409 other | `ConflictError` | State conflict; read current state first. |
| 410 `stream_expired` | `StreamExpiredError` | SSE retention window passed. Use `get_run`; `get_run_events` reports `streamExpired: true` and falls back automatically. |
| 400 `invalid_last_event_id` | `InvalidEventCursorError` | Cursor belongs to another run. `get_run_events` reports `cursorInvalid: true`; call again without `afterEventId`. |
| 400 / 422 | `BadRequestError` | The API's message is passed through verbatim so the model can fix its input. |
| 429 | `RateLimitedError` | Carries `retryAfterMs` plus any `X-RateLimit-*` headers. |
| 5xx | `ServerError` | GETs already retried 3×. |
| fetch failed | `NetworkError` | No HTTP response was produced. |
| response shape mismatch | `ResponseValidationError` | Beta drift: the tool text carries up to 20 zod issues **and** the raw body (truncated at 4000 chars). |
| local budget exhausted | `LocalRateLimitError` | Nothing was sent; safe to retry later. |

Every one of these is returned as an MCP `isError` result containing
`<ErrorClassName>: <message>` plus a `helpUrl` if the API gave one and a guidance line telling the model what to
do next — never as a transport-level throw.

### The never-retry-on-create rule

Cursor v1 has **no idempotency key**. This client retries `GET` only (429, 5xx, network; 3 attempts, exponential
backoff with full jitter, honouring `Retry-After` up to 30s per wait). `POST` and `DELETE` are never retried,
because a blind retry of `POST /v1/agents` launches a second cloud agent and a retry of
`POST /v1/agents/{id}/runs` queues a second run. If a write fails with a 5xx or a network error, the work may
still have started — call `list_agents` / `list_runs` before resending.

The one retry-safe create is a client-supplied `agentId` (`bc-<uuid>`) on `launch_agent`. Re-sending the same id
returns `409 agent_id_conflict`, which this server catches and turns into the existing agent plus
`alreadyExisted: true`. `agentId` cannot be combined with `envVars`.

> `envVars` is **beta-gated and silently ignored** when the account does not have it: the request still returns
> 201 with the variables dropped. Verify inside the agent before relying on them.

## Development

```bash
pnpm install
pnpm typecheck
pnpm test:unit        # msw-backed; no network
pnpm test:contract    # spawns the CLI over stdio and drives it with the MCP SDK client
pnpm build
pnpm smoke            # build, boot dist/cli.js, print the tool list
```

`pnpm-workspace.yaml` is not a workspace declaration: it is where pnpm 11 keeps its build-script decisions
(allow `esbuild`, decline msw's browser-only postinstall). Without it `pnpm install --frozen-lockfile` exits 1 on
a clean checkout. npm ignores the file, so installs from git are unaffected.

Integration tests hit the real API and are skipped unless both variables are set:

```bash
RUN_INTEGRATION=1 CURSOR_API_KEY=crsr_... pnpm test:integration
```

They launch a no-repo agent with a trivial prompt, poll it to a terminal status, and delete it in a `finally`.

### Live smoke tests

Two scripts drive the built server over real MCP stdio against the real `https://api.cursor.com`. **Both need
`CURSOR_API_KEY`, both cost real agent minutes, and neither runs in CI.** Build first (`pnpm build`).

```bash
CURSOR_API_KEY=crsr_... pnpm live:suite
CURSOR_API_KEY=crsr_... REPO_URL=https://github.com/your-org/your-repo pnpm live:repo launch
CURSOR_API_KEY=crsr_... pnpm live:repo monitor <agentId> <runId>
```

- `live:suite` walks every tool end to end. It creates **one** no-repo agent and **deletes** it in a `finally`.
- `live:repo` launches a real agent on `REPO_URL` in two phases — `launch` prints the `agentId`/`runId` (and
  survives a pending launch), `monitor <agentId> <runId>` follows it to a terminal status — and **archives** the
  agent when it is done.

**Release notes.** `files` ships only `dist/`, `README.md` and `LICENSE`; `dist/` is gitignored. The `prepare`
script runs `npm run build` (npm, not pnpm — npm is what actually runs it during a git install), and npm runs
`prepare` with devDependencies installed for git dependencies — that is what makes `npx -y github:...` work
without a committed build. Verified end to end: a cold `npx -y github:ColtonGlasgow13/cursor-cloud-agents-mcp
--version` on a machine with GitHub SSH access takes ~26s and prints the version. Bump `version` in
`package.json` and tag the commit so installs can pin `#vX.Y.Z` (the tag has to exist first).

## Out of scope

- **Private worker pools / self-hosted workers** (`/v0/private-workers*`, `POST /v1/sub-tokens`) — a different
  product surface that needs a team service-account key.
- **Webhooks** — Cursor v1 does not have them yet ("coming soon"; only legacy v0 supports them). Poll
  `get_run_events` / `wait_for_run` instead.
- **The local `cursor-agent` CLI** — this server only talks to the cloud REST API.
- **Conversation history** — v1 has no endpoint for it. `run.result` and the SSE events you capture are all
  there is.
